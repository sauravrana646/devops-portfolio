A new service should not require its developer to choose an APM SDK, wire exporters, and learn a different tracing recipe for every language. The ownership model that scales is simpler: **the platform team supplies instrumentation; application teams write ordinary Java and Python code**.

Here is how that looks in practice. A request enters a Spring Boot API, crosses two FastAPI services, reads and writes PostgreSQL, and calls an OpenAI-compatible LLM provider. One trace follows the request. Grafana shows rates, latency, token metrics, logs, and a waterfall; Jaeger offers a second trace UI. The [companion repository](https://github.com/sauravrana646/otel-chaos-poc) holds the manifests, application code, CLI, and tests behind this walkthrough.

![Request path and telemetry: business flow above, OpenTelemetry Collector and backends below](/blog/otel-zero-code/request-and-telemetry.svg)

A **trace** is the story of one request. A **span** is one timed step in that story, such as an HTTP call or SQL query. **Metrics** aggregate many requests into rates and latency percentiles. **Logs** provide detailed events. A shared trace ID connects the steps; the application does not need to manufacture one.

## What the platform runs

The stack uses Kubernetes with Argo CD, Grafana, and Prometheus already available. Argo CD deploys the OpenTelemetry Operator, the three application services, a deterministic LLM mock, CloudNativePG, the OpenTelemetry Collector, Tempo, Jaeger, Loki, dashboards, and Toxiproxy. k6 generates traffic. The numbers below come from a local cluster run used to validate the pattern—not as a capacity claim.

The request starts with a small JSON document:

```json
{
  "request_id": "blog-example-20261004-01",
  "item_id": "item-100",
  "scenario": "normal",
  "provider": "mock"
}
```

`java-api` reads the catalog item with JDBC and calls `python-analysis`. That service reads context with psycopg and calls `python-llm` through HTTPX. The LLM service checks for an existing result, calls either the mock or OpenRouter through the OpenAI-compatible Python client, and writes the result to PostgreSQL. For the request above, the live mock response was:

```json
{
  "request_id": "blog-example-20261004-01",
  "result": "mock-recommendation for blog-example-20261004-01 scenario=normal",
  "model": "mock-gpt",
  "status": "ok"
}
```

`provider` defaults to `mock`. OpenRouter is selected for an individual request by passing `"provider": "openrouter"` or the CLI's `--provider openrouter` flag. It does not change the Deployment or affect later mock requests. That lets you prove the instrumentation path before spending money on a real model.

## Install the operator with GitOps

The root Argo CD Application points at child Applications. One child installs the OpenTelemetry Operator Helm chart. Its webhook is limited to namespaces carrying `otel-injection: enabled`; the application namespace has that label. Other children install the Collector, Instrumentation resources, CloudNativePG, applications, and dashboards. Bootstrap syncs these in dependency order.

![Argo CD Application fields for the OpenTelemetry Operator, including the namespace selector](/blog/otel-zero-code/gitops-operator.svg)

```yaml
# platform/argocd/applications/apps.yaml (selected fields)
source:
  repoURL: https://open-telemetry.github.io/opentelemetry-helm-charts
  chart: opentelemetry-operator
  targetRevision: 0.124.0
  helm:
    valuesObject:
      admissionWebhooks:
        namespaceSelector:
          matchLabels:
            otel-injection: enabled
```

This is the first standardization point. The platform owns the operator version and its allowed namespace scope. Developers do not add an SDK to every service just to participate in tracing.

## Opt each workload in by language

Kubernetes does not infer a container's programming language. Declare it on the **pod template**, so every newly created pod passes through the operator's admission webhook. The annotation value names an `Instrumentation` resource in the same namespace.

![Java and Python pod-template annotations for OpenTelemetry injection](/blog/otel-zero-code/pod-annotations.svg)

```yaml
# java-api
spec:
  template:
    metadata:
      annotations:
        instrumentation.opentelemetry.io/inject-java: java

# python-analysis
instrumentation.opentelemetry.io/inject-python: python-web

# python-llm
instrumentation.opentelemetry.io/inject-python: python-genai
```

When Kubernetes creates a matching pod, the webhook adds an init container and a shared volume before the app starts. On a live Java pod that looks like an `opentelemetry-auto-instrumentation-java` init container, `JAVA_TOOL_OPTIONS`, and an agent mount. On a Python pod it looks like an `opentelemetry-auto-instrumentation-python` init container, `PYTHONPATH`, and `/otel-auto-instrumentation-python`. Those are **generated pod fields**; they are not handwritten in the application Deployment. Edit the Deployment template and let it roll out new pods—do not patch a running pod by hand.

The mock server deliberately has no injection annotation. You see the LLM service's outbound HTTP span, but not a corresponding server span inside that mock. That boundary is useful: automatic instrumentation covers what you opt in.

## Define the agent and its export settings

An `Instrumentation` custom resource tells the operator which agent image to copy into the pod and where to send telemetry. Use one Java profile and two Python profiles: `python-web` for ordinary web and database work, and `python-genai` for the LLM service.

![Instrumentation resource selected fields for the Python GenAI profile](/blog/otel-zero-code/instrumentation-cr.svg)

```yaml
# platform/otel/instrumentation/instrumentation.yaml (selected fields)
apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: python-genai
  namespace: apps
spec:
  exporter:
    endpoint: http://otel-collector.observability.svc:4318
  propagators:
    - tracecontext
    - baggage
  sampler:
    type: parentbased_traceidratio
    argument: "1.0"
  python:
    image: platform/python-instrumentation-genai:<tag>
```

`tracecontext` carries the trace identity across Java and Python HTTP calls. A `1.0` sampling setting keeps every trace while you validate the path; production sampling and retention need a separate decision. The Java profile uses the upstream Java auto-instrumentation image. The Python profiles use images built by the platform from pinned instrumentor packages.

![Pinned Python auto-instrumentation packages](/blog/otel-zero-code/python-packages.svg)

```text
opentelemetry-distro==0.51b0
opentelemetry-instrumentation-fastapi==0.51b0
opentelemetry-instrumentation-httpx==0.51b0
opentelemetry-instrumentation-psycopg==0.51b0
opentelemetry-instrumentation-logging==0.51b0
# python-genai adds:
opentelemetry-instrumentation-openai-v2==2.1b0
```

Python auto-instrumentation patches supported library calls at startup. That gives FastAPI server spans, HTTPX client spans, psycopg database spans, and OpenAI client / GenAI telemetry. It does **not** automatically time every function in pandas, numpy, scikit-learn, or arbitrary business code. The Spring Boot API similarly gets HTTP, JDBC, JVM, and supported client visibility from the Java agent. None of the application source initializes an OpenTelemetry SDK or creates a custom span.

## Route signals through one Collector

The Collector is the routing point. Agents send OTLP to it. It sends traces to **both** Tempo and Jaeger, exposes metrics for Prometheus to scrape, and sends logs to Loki. The trace pipeline also feeds span-metrics and service-graph connectors. Grafana reads Tempo, Prometheus, and Loki; Jaeger has its own UI and trace storage.

![Collector pipelines for traces, metrics, and logs](/blog/otel-zero-code/collector-pipelines.svg)

```yaml
# platform/observability/collector.yaml (selected fields)
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, filter/drop_health, resource, batch]
      exporters: [otlp/tempo, otlp/jaeger, spanmetrics, servicegraph]
    metrics:
      receivers: [otlp, spanmetrics, servicegraph]
      exporters: [prometheus]
    logs:
      receivers: [otlp]
      exporters: [otlphttp/loki]
```

The Collector removes health-probe spans so `/healthz` and `/readyz` do not bury useful requests. Prometheus also scrapes CloudNativePG database metrics through a PodMonitor. PostgreSQL server logs are collected separately. A database **client span** tells you which application query was slow; a PostgreSQL log can tell you what the server reported. Server logs do not automatically carry the application's trace ID.

## Give PostgreSQL a clear owner

CloudNativePG creates the PostgreSQL instance and its persistent volume from a `Cluster` resource. The walkthrough uses one PostgreSQL 17 instance and a small local volume. A seed Job creates the catalog and recommendation tables. The database credential is a Kubernetes Secret created at bootstrap, not committed to Git.

![CloudNativePG Cluster selected fields](/blog/otel-zero-code/cnpg-cluster.svg)

```yaml
# platform/cnpg/cluster.yaml (selected fields)
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: app-postgres
spec:
  instances: 1
  imageName: ghcr.io/cloudnative-pg/postgresql:17
  storage:
    size: 2Gi
    storageClass: local-path
```

The Operator does not inject a Java or Python agent into PostgreSQL. Trace database calls from the application side and observe database health through CloudNativePG metrics and logs. Jaeger can use its own PVC and span TTL according to your retention policy.

## Prove one request crossed the stack

From the companion repository checkout, start with the health check and a deterministic smoke test:

```bash
./cli/poc doctor
./cli/poc smoke --mock
```

The smoke command sends a request through `java-api`, reads its trace ID, and checks that the expected services and spans arrived. One validated run returned trace ID `1e7e059ed9f9bef0911fa9aabf62ac2e`. The same request appeared in Grafana's Tempo data source and in Jaeger.

![Grafana Tempo waterfall for an end-to-end recommendation request](/blog/otel-zero-code/grafana-trace.jpg)

Read the waterfall **from left to right**. The root `java-api POST /api/recommendations` took **808.59 ms**. Its JDBC catalog `SELECT` took **9.04 ms**. The Java outbound `POST` took **755.99 ms**, containing `python-analysis POST /analyze` at **719.86 ms**. Analysis spent **3.51 ms** on its database `SELECT`, then called `python-llm`. The LLM service `POST /generate` took **373.07 ms**; within it, `chat mock-gpt` took **212.12 ms** and the database `INSERT` took **6.02 ms**. Parent spans include their children, so adding all those durations would double-count time. The wide horizontal gaps and bars show where to investigate next.

![The same trace in Jaeger, showing the three instrumented services and nested spans](/blog/otel-zero-code/jaeger-trace.jpg)

For your own trace, port-forward Jaeger and open `http://localhost:16686/trace/<trace-id>`:

```bash
kubectl -n otel-poc-observability port-forward svc/jaeger 16686:16686
```

Jaeger shows three instrumented services and 18 spans in this captured request. An **Incomplete** badge means the span tree is not fully represented—the uninstrumented mock server is one known boundary. HTTP 200 and the smoke assertion establish that the request itself succeeded.

## Add controlled load, then read the dashboards

The companion CLI wraps k6's `constant-arrival-rate` scenario. One iteration sends one recommendation request with a unique `request_id`; k6 schedules starts at the chosen rate, independently of how long each request takes. A slow service should show rising latency or dropped starts instead of silently reducing the offered load.

```bash
./cli/poc load --scenario constant --provider mock --rps 1 --duration 30s
```

On a validated mock run, k6 completed **31 HTTP requests** in roughly 30 seconds, with **0 failed requests**, **0 dropped iterations**, **228 ms average**, **396.85 ms p95**, and **903.99 ms maximum** HTTP duration. The observed rate was about **1.02 requests/second**. Treat that as one short sample, not a capacity claim; scrape windows make dashboard point values differ slightly from the configured rate.

![Grafana overview dashboard during steady mock load: ingress rate, errors, and latency](/blog/otel-zero-code/grafana-overview.jpg)

The Overview dashboard answers, “How much traffic arrived, how often did it fail, and how long did it take?” It also compares server RPS and p95 latency across Java, analysis, and LLM services. The LLM dashboard answers a different question: “How many tokens and model calls did the instrumented SDK report?”

![Grafana LLM dashboard during mock load: token and operation metrics](/blog/otel-zero-code/grafana-llm.jpg)

Displayed tokens are **mock-provider telemetry**. They do not prove OpenRouter usage or billing. When testing a real model, check the response's `model` field and the GenAI span's model attribute before interpreting model-specific token panels. A model can also return missing or differently mapped usage data; absence in a dashboard is not proof of zero tokens.

For a latency experiment, keep load running in one terminal, then inject one bounded fault in another:

```bash
./cli/poc load --scenario constant --provider mock --rps 2 --duration 2m
# In a second terminal, while load is active:
POC_FAULT_TTL_SECONDS=60 ./cli/poc fault --scenario latency --provider mock
./cli/poc reset
```

Toxiproxy sits on selected database and HTTP dependency paths. The fault command adds a named toxic with a cleanup TTL; `reset` removes known toxics and verifies they are gone while retaining PostgreSQL data. For retries, `./cli/poc retry --provider mock --scenario success` shows a provider failure followed by recovery, and `--scenario exhaust` shows exhausting attempts. Compare the new waterfall and error-rate panel with the baseline instead of relying only on the CLI exit code.

## What changes for a real model provider

Use a real provider only when you explicitly select it. Configure the model and key through the CLI, verify that every LLM pod has the current Secret projection, then run a bounded test:

```bash
# Supply the provider API key from a secure local source; never commit it.
./cli/poc openrouter update --model '<provider/model-id>'
./cli/poc openrouter verify
./cli/poc smoke --openrouter
./cli/poc load --scenario constant --provider openrouter --rps 1 --duration 30s
```

`openrouter verify` prints the selected model and a **masked** key. Load and retry commands verify the mounted credentials once and proceed when they match. Real-provider traffic can cost money and hit rate limits. The outbound client span shows time up to the provider response; it cannot show the provider's internal queueing, routing, or model execution spans.

## What this pattern standardizes

The platform can give each team a pod annotation, a compatible agent profile, a shared Collector endpoint, and ready-to-use dashboards. Developers still own meaningful names, safe data handling, and any business spans that automatic library instrumentation cannot see. Auto-instrumentation covers supported frameworks and libraries, not arbitrary Python functions or every package in a requirements file. Verify each runtime and instrumentor combination with a real trace before you treat this as a production standard.
